# pr-checklist

Run every item before a PR is opened, and again before it is marked ready after review changes. Report each item as pass, fix, or n/a with one line of evidence. An item that fails blocks opening until fixed. Draws on `decision-gate` (need) and `ground-truth-discipline` (verify claims).

## The checklist

1. **Main can't already do it.** Ask this first, before designing anything: could main's existing code do this, as is or with a small change? Search main by the behavior, not by your mechanism's name. For every main flag or option near the behavior, read each code path it touches and check that yours honors it: a flag ignored on your path is a one-line fix, not a reason for a new mechanism. Name the closest existing mechanism and why it falls short. Give one reviewer the bare need without your design and ask the same question. *(Receipt: a claim that main lacked a fix; main already had it process-wide.)* *(Receipt: an 80-line mission split and its 145-line test went through five review rounds; main's per-dataset `over_shard: false` covered it once passed through to the scene split, and the reviewer who wrote that flag caught it on first read.)*
2. **Need on the real path.** State the measured effect on the path that matters (the vehicle, the export, a trained-model difference). Equivalence alone is not need. *(Receipt: a PR proving a switch was bit-equivalent was closed — the vehicle already ran the alternative.)* A bug with a measured consequence is need; fix it narrowly rather than disclose side effects. Name the module that consumes the measured signal in the config the PR affects. *(Receipt: a train/eval gap was measured on features the affected config's trained head never reads.)* A latency or memory need is measured on the deployment runtime and version, not an intermediate one. *(Receipt: a node costing 70 ms in ONNX Runtime cost 1 ms in the deployed TensorRT build.)* A fix for one resource is measured on the others in the same smoke: a memory fix states its throughput against the reference run. *(Receipt: a memory fix passed its smoke at 78.6% host memory; the full run then trained at ~9 steps/min against ~16 before, about four node-hours more per run, found only from the full run.)* *(Receipt: a 332-line converter for raw recordings that existed only on the author's machine was readied for main; it rebuilt shards already released and trained on, so nobody else could run it or needed it. A PR whose only input lives with its author has no need on main; keep the branch as the receipt.)* For legacy data, convert it once into the format main already reads and store the output; the converter stays on its branch.
3. **Built from main's mechanism and names.** Extend what main has; no side paths. Reuse main's vocabulary. *(Receipt: a side-file join was rejected; the same need landed as a data column main already read.)* Data a consumer reads lives in the primary artifact's schema (a column the consumer's loader already reads), written by the producer (e.g. the labeler writes every training input as a shard column, like the speed column); a file added beside a released artifact is debt to retire, never a pattern to repeat. *(Receipt: four side files accumulated next to write-once label shards (set speed, column transforms, steering targets, provenance), each with its own reader, upload and gate; the steering targets were left unported while every label check passed.)* Size a port by what it needs in its new home, not by the research code's line count: scaffolding that rebuilds state the new home already has (configs, model instances, its own solvers) goes away. Design the minimal version before a size goes on a plan. *(Receipt: a 2,311-line target builder sat on a roadmap at that size; most of it instantiated a model to reach state the producer already held and re-implemented solvers the producer already had.)*
4. **Invariant to which model ships.** Mechanisms behind flags that default off; recipe values (weights, members, on/off choices) only in a final config change. With the flag off, main's path is bit-identical — a test proves it. A recipe value means the same on any node count, sharding or loader option; a knob for memory or coverage must not also move what the value means. *(Receipt: a sampler that scaled split datasets by their split count made one recipe draw DAgger at 44% on one node and 2.4% on four, and turned a memory flag into a 32x change in a dataset's share.)*
5. **Cut from the latest main.** 0 commits behind at open; merge main (never rebase or force-push) when it moves. After a merge, search for silent breaks the merge didn't flag (APIs main changed, e.g. a list that became a dict).
6. **Bite-sized and independent.** `git diff origin/main...HEAD --stat` lists only the intended files. Test lines count: one focused test file, only the tests the claim needs. Two open PRs share no files. Set the line budget, tests included, before building; a brief for PR-bound code states it as a gate. Code moved to main is the minimum a coverage audit justifies, proven equal by a regression test, never history copied verbatim. A series that ships a tool traces every output it claims from inputs the team has (code and data) through main plus the series before its first PR, passes an end-to-end run from a fresh clone before its last, and after merge the author's own work uses it. *(Receipt: a five-PR evaluation suite was found mid-series to need box-only scenes and a private replay path.)*
7. **Every claim verified.** Each number in the description comes from a run you can point to; read that run's own logged config and confirm the code under review produced it (no option the PR lacks) and that its reference differs only in the claimed variable, also when reviewing another's PR; scope each claim to what was measured; say what wasn't run on main if the evidence came from another branch. For anything on the export or runtime path, diff the new interface (inputs, outputs, defaults) against the artifact actually deployed, not only against main's code. For a config or rename, diff what the change produces (the fully resolved config, derived names, hashes and counts) against its base, not only the keys meant to change. Before opening or revising, an independent agent tries to refute each claim (`ground-truth-discipline`, Principle 4). *(Receipts: a set-speed export carried 2 of the 3 inputs the shipped bundle takes; a training config's recipe silently replaced its base's BEV range and window; a PR's closed-loop table came from a checkpoint trained with a loss option the PR did not contain, against a baseline without the PR's teacher term.)*
8. **Reproduced from outside.** For a PR series that together claims a workflow, the clean room is the whole workflow, 0 to 100, from a fresh clone of main plus the open PRs in merge order: a runner with only the clone and a one-page task produces the end result and matches the reference; any step that needs something outside the clone is a failure. Per-PR reproduction is necessary, never sufficient. Before opening, a clean room reproduces every number in the description: a fresh container from main's image on no shared mounts (no work dirs, notes, memory or local tool wrappers), a fresh clone of the pushed branch, read-only shared inputs (S3, registry) and the description and usage text only; it is told no expected values. Each guess it has to make is a blocker. Its PASS is recorded for the exact commit and the open command refuses without it. A PR in a series opens only after the whole series passes. *(Receipt: refuters found box-only inputs, two number-changing bugs and a check that scanned nothing in a stack whose own checks had all passed on the machine that built it.)* *(Receipt: four per-PR clean rooms passed while the chain from main could not train the shipped model's recipe.)*
9. **Converged, not reviewed once.** A large PR, a port, a newly developed method, or the plan that sequences several PRs, is reviewed in rounds until it reaches a fixed point: each round a fresh independent reviewer that has not seen earlier rounds, then the cuts and fixes, then the full equivalence or regression check (a round that breaks it is reverted, not patched); when the full gate takes hours, each round runs a representative slice that includes the extremes (largest inputs, each map), and the full gate runs once on the final tip; stop when two consecutive rounds change less than 2% or the reviewer finds only cosmetic items. One pass is never the stopping rule. *(Receipt: a labeler port went 8,530 -> 5,017 -> 4,466 lines with bit-identical output every round; each fresh round found what the previous one missed.)* *(Receipt: a 58-member bit-identity gate took 8-10 h, which would have made every review round a night long; a 6-member slice per round plus one full run kept the fixed point reachable.)* Check the stop against the rule's numbers, not the reviewer's prose: 'stopped at round N' with the last rounds above the threshold is not converged, and any commit after the last round reopens it. *(Receipt: a PR reported as reviewed after five rounds changing 35, 9, 15 and 11%; a later commit and a 345-line test file had never been in a round.)* A cut that moves a step out of the repo is checked against the workflow the PR exists for: the clean room starts from that workflow's real input (the raw recording), not from an intermediate the cut made. *(Receipt: a labeler series lost 1,023 lines by moving the recording reader to a one-off converter outside the repo; the series then labeled only pre-converted episodes, and 'record, then label from main' no longer worked.)* For a plan, the gate each round is its completeness map (every source item mapped or 'not needed because', none unmapped) plus the checklist on each planned PR; and it converges only after the measurements that keep or drop its rows are in. When successive rounds each find one bug of the same class, stop fixing instances: name the class, add one test family that covers it across every input, then review again. *(Receipts: a 73-row roadmap ran 12 rounds without converging (27 -> 9 findings, a third of rows changing per round) while the runs that would keep or drop its largest rows were still training; a labeling review ran 15 rounds, the last five each finding one rare-input bug of one class.)* Ground rules for every fixed-point review (code, method or plan): **settled stays settled**: keep a decision log (each settled item with its reason and receipt, plus the given facts such as what main has and measured numbers, marked locked); every reviewer gets it and reopens a locked item only by citing evidence not in its receipt, since a reviewer that has not seen earlier rounds otherwise re-proposes what they reversed. **Freeze the input**: rounds run on a fixed snapshot; evidence that lands mid-loop is folded once, between rounds, as new locked items. **Review the decisions, not the reference**: for a plan, the reviewed object is its one-page decision list (items, scope, order, sizes), and long detail is reference. **Count decisions, not wording**: converged = two rounds with no change to the decisions (for code, to behavior or the gate). **Cap a plan's loop**: at most three rounds once its evidence is in; what is still disputed goes to the owner as a call. *(Receipt: a 64-row roadmap ran 23 rounds; one PR was merged in round 22 and split out again in round 23, and the PR count went 27 -> 26 -> 27. The owner: reviewers should not start from scratch for settled items and given facts.)*
10. **Checks run.** Lint and type-check on the changed files; tests named explicitly (a missing path collects nothing and passes); gated tests (e.g. export) run with their gate on. Never bypass hooks. Judge each new test by mutation: break the code it claims to guard and keep only tests that then fail; a test no mutant can fail is cut. *(Receipt: reviewers mutated a loader change 16-19 ways per round; a 345-line test file fell to 79 lines and two unprotected claims got tests.)* Measure each new test's peak memory and wall time; a test that needs more than the CI runner has is a failing test. Before calling a red CI infrastructure (lost runner, exit 137), rule out the PR's own tests by that measurement. *(Receipt: a config PR's one new test peaked at 38.5 GB; CI died twice, first read as a lost runner.)*
11. **Lean description, final length the first time.** Title `type(area): description`. First person. Description ≤ ~15 lines with at most one evidence table (headline rows only); test plan ≤ 3 bullets. No tool attribution line. Cold and factual: what the code does and what was measured; no inferred consequences; cut any sentence the reviewer does not need.
12. **Review order.** Copilot review first, fix, then a human reviewer. Posting, opening or commenting needs the owner's go.
